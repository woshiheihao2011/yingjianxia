用户注册登录、JWT 鉴权、个人中心、店铺管理完成。API 网关 + Nacos + CI/CD 就绪。前端可登录注册。

第 5 周末

★ M2 — 商品上架与验机

★ M3 — 核心交易闭环

第 9 周末

★ M4 — 售后与物流闭环

发货管理、物流轨迹、售后申请/审核/仲裁/退款、消息推送、评价管理全部完成。4 大业务流程 E2E 可跑通。

第 14 周末

★ M5 — 正式上线

全部 15 个微服务、31 个页面、170 条测试用例全部通过。性能、安全指标达标。UAT 签字确认。灰度发布→正式上线。

用户服务 BE-1

  • 手机号注册：验证码发送（Redis 60s 防刷）、BCrypt 加密、JWT Token 生成

  • Token 黑名单（Redis SET）：登出/改密后旧 Token 失效
  • 密码安全：连续 5 次错误锁定 30 分钟，找回密码防泄露
  • 个人中心：资料查看/修改、信用分查询
  • 实名认证：对接公安二要素/三要素 API（Mock）
  • 信用分算法实现 + XXL-Job 每日凌晨批量刷新
  • 收货地址 CRUD
店铺子模块 BE-1

  • 退货地址、默认快递（顺丰/圆通/中通/韵达/EMS）
  • 高级设置：接受砍价、支持面交、发货时效承诺（24/48/72h）
  • 店铺评分/粉丝/成交量/在售数冗余字段 + 事件驱动更新
  • 优质卖家认证条件：成交量≥50、好评率≥95%、纠纷率≤2%
API 网关与鉴权 BE-5
  • Spring Cloud Gateway 路由配置（按路径前缀路由到微服务）
  • JWT Token 全局过滤器：校验 → 解析 userId 注入请求头
  • Sentinel 限流熔断：API 维度 + 用户维度双重限流
  • CORS 跨域统一配置
  • 灰度发布路由：基于请求头路由到灰度实例
前端页面 FE-3

Sprint 2 Phase 2 — 商品与验机（商品 + 验机 + 审核 + ES 搜索）

商品服务 BE-2

  • 商品状态机：草稿/审核中/在售/已售/下架/审核拒绝
  • 商品图片上传 OSS（WebP 格式）+ 封面设置

验机服务 BE-2
  • db_inspection 建表：inspection_reports, inspection_items, inspection_templates
  • 创建检测任务（幂等：已有进行中任务返回已有 ID）

  • SHA-256 数字签名生成（productId|grade|result|inspectorId|items|timestamp + SALT）
  • 验机报告 PDF 生成 + OSS 上传，降级返回 JSON
  • 报告公开查询接口（GET /api/v1/inspections/{productId}/report）
  • InspectionCompletedEvent 发送 → 商品服务消费后上架
  • 收货 48h 未完成检测预警
审核服务 + ES 搜索 BE-5
  • db_support 建表审核相关表
  • 机审接口对接阿里云内容安全（Mock）
  • 两级阈值：低于阈值直接通过，高于直接拒绝，中间人工审核
  • 机审不可用时降级为全部待人工审核（禁止直接放行）
  • 人审队列 + 审核员操作（通过/拒绝）
  • ProductAuditPassedEvent 发送 → 商品状态改为"在售"
  • Canal 监听 MySQL binlog → RocketMQ → ES 同步消费者
  • ES 索引 Mapping 创建（keyword/text ik/scaled_float 等）
  • 商品搜索：关键词 + 分类多选 + 成色单选 + 价格区间 + 地区 + 排序

Sprint 3 Phase 3 — 核心交易（订单 + 担保 + 支付 + 营销）

📅 第 6-7 周 👤 BE-3 + BE-4 + FE-1 + FE-2 🎯 M3 核心交易闭环
订单服务 BE-3 核心难点
  • db_order 建表：orders, order_items, cart_items, order_status_logs
  • 购物车 CRUD（Redis 高频读写 + MySQL 持久化）
  • 创建订单 TCC Try 流程： ① 批量查询商品 + 校验库存
    ② 调用营销服务计算优惠
    ③ 商品服务 Try 预扣库存（Redis Lua）
    ④ 担保交易 Try 冻结资金
    ⑤ 创建订单 + 订单明细 + 商品快照
    ⑥ 发送 OrderCreatedEvent
  • 支付成功 Saga Confirm 流程： ① 消费 PaymentSuccessEvent（幂等键 orderId）
    ② 担保交易 Confirm 确认冻结
    ③ 商品服务 Confirm 实扣库存（MySQL 乐观锁）
    ④ 订单状态 → 待发货
    ⑤ 发送 OrderPaidEvent
  • 订单取消 TCC Cancel 流程：Redis 库存回补 + 担保资金解冻
  • 订单状态机引擎（Spring StateMachine）+ 状态变更日志表
  • 超时取消：XXL-Job 每分钟扫描待付款订单
  • 超时自动确认：XXL-Job 每小时扫描待收货订单（7 天）
  • 支付回调幂等：order_id + channel_tx_no 唯一键
  • 买家/卖家双角色视图
担保交易服务 BE-3 核心难点
  • db_escrow 建表：wallets, escrow_records, transactions, withdrawal_records, recharge_records
  • TCC Try：买家可用余额 -amount，冻结 +amount（乐观锁 + 幂等键）
  • TCC Confirm：escrow_records status=已冻结，不可逆
  • TCC Cancel：解冻回买家（处理空回滚 + 悬挂）
  • 确认收货放款：手续费 1% → 卖家可用余额 +settle_amount
  • 卖家账号冻结 → 放款到冻结余额（不可提现）
  • 售后退款（已冻结/已放款两种场景）
  • 每日三方对账任务：担保 = 钱包 = 流水
  • Outbox Pattern 实现：本地事务写业务 + 事件表
支付服务 BE-4
  • 发起支付：创建支付单 → 调用第三方统一下单 API（Mock）
  • 支付回调：验签 + 幂等校验 → 更新支付单 → 发送 PaymentSuccessEvent
  • 主动查询兜底：定时查询待支付订单状态
  • 钱包余额查询、收支明细
  • 充值：预设金额 + 自定义金额
  • 提现：二次验证（短信 + 支付密码）+ 限额（单笔 5 万/日 20 万/日 3 次）
  • 新绑定提现账户 24h 内不可提现
  • 提现失败退回余额
  • 支付回调迟到 → 订单已取消 → 触发退款
营销服务（基础） BE-4
  • db_support 营销相关建表：coupons, coupon_records, promotions, points_records
  • 优惠券创建/领取/锁定/核销/解锁闭环
  • 优惠券防超发：Redis 预扣 + DB 乐观锁
  • 优惠价格计算接口（内部 RPC）
  • 积分基础：签到 +5、完成订单积分
前端页面 FE-1 FE-2
  • cart.html：购物车（商品列表 + 结算侧栏 + 支付方式选择）
  • orders.html：订单中心（角色切换 + 状态 Tab + 订单卡片 + 操作按钮）
  • wallet.html：钱包（余额卡片 + 充值/提现 + 支付方式 + 安全设置）
  • transactions.html：收支明细（汇总卡 + 筛选 + 可展开列表）
  • coupons.html：优惠券/积分（积分卡片 + 优惠券 Tab + 领券中心 + 积分兑换）

环境分层
DEV
开发联调环境 — 各开发人员本地 Docker Compose 或共享 DEV 集群。开发自造数据，可自由重启服务。 K8s 命名空间：dev。每日自动构建最新镜像部署。
SIT
系统集成测试环境 — QA 主导。测试造数脚本批量生成数据（买家/卖家各 50+，6 品类各 20+ 商品，各状态订单）。 K8s 命名空间：sit。所有 Mock/Stub 服务可用。
UAT
用户验收测试环境 — 接近生产数据。使用生产快照脱敏数据。 K8s 命名空间：uat。业务方在此验收。
PRE
预发布环境 — 生产配置 + 生产快照脱敏数据。灰度发布前验证。 K8s 命名空间：pre。与生产同规格部署。

9 开发规范与协作机制
确保 10+ 人团队高效协作的规范约定
代码规范
  • 后端遵循阿里巴巴 Java 开发手册 + DDD 分层架构（API/App/Domain/Infrastructure）
  • 前端遵循 Vue 3 Composition API + <script setup> 语法
  • 所有写操作 API 必须携带 Idempotency-Key 请求头
  • 统一响应体：{ code, message, data, timestamp }
  • 错误码分段：用户域 20xxx / 商品域 30xxx / 订单域 40xxx / 资金域 50xxx / 售后域 60xxx / 营销域 70xxx
  • 数据库表必须包含：雪花 ID、created_at、updated_at、version（乐观锁）
  • 资金操作表必须包含：idempotency_key（UNIQUE）、唯一约束
  • Git 分支策略：main → develop → feature/xxx → MR → Code Review → 合并
  • 提交信息格式：type(scope): subject（feat/fix/refactor/test/docs）
协作机制
  • 每日站会：09:30，每人汇报昨日完成/今日计划/阻塞问题
  • Sprint 评审：每个 Sprint 结束日演示功能，QA 参与验证
  • 代码审查：所有 MR 必须至少 1 人 Review 后合并
  • 接口联调：前后端按 API 文档（Swagger/OpenAPI）联调，后端先出 Mock 接口
  • 缺陷跟踪：使用 GitLab Issues 管理，P0 缺陷群通知
  • 周报：每周五下午输出进度周报，同步里程碑达成情况
  • 技术评审：关键设计变更需 Tech Lead 评审通过
  • 知识库：使用飞书文档维护技术决策记录和 API 文档
